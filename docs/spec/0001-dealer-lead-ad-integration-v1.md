# Spec: 经销商线索×广告投放整合桌面客户端 v1

## Problem Statement（问题陈述）

经销商的线索在巨懂车经营后台里（按门店分账号管理），广告投放数据在巨量引擎里（按广告账户管理）。想回答「每个门店今天花了多少钱、来了多少线索、单条线索成本多少」，需要在两个平台之间来回切换、人工导出、手工拼 Excel——费时、易错，门店一多就无法维持。

## Solution（解决方案）

一个跨 PC 平台的桌面客户端（Windows 优先、macOS 次之），运营者与助理自用的只读工具。添加门店并登录其巨懂车账号、OAuth 授权巨量引擎广告账户后，客户端自动定时拉取两边数据到本地 SQLite，提供：

- **汇总看板**：各门店线索量、广告消耗、线索成本、ROI 趋势，可按时间范围与门店切换；
- **线索明细**：按时间/门店/状态等筛选，含完整手机号；
- **导出 Excel**：看板数据与线索明细。

不做线索跟进/分配管理（DMS 职能）。

## User Stories（用户故事）

1. 作为运营者，我想添加一个门店并登录其巨懂车账号，以便系统能拉取该门店的线索。
2. 作为运营者，我想在应用内完成巨懂车登录（账号密码或短信验证码均可），以便滑块、短信等人工环节不离开客户端。
3. 作为运营者，我希望登录一次后会话被长期复用，以便减少重新登录次数、降低风控暴露。
4. 作为运营者，当会话失效时，我想让客户端自动用保存的账号密码重新登录，以便我不在场时采集也能恢复。
5. 作为运营者，当自动重登被滑块/风控拦截时，我想收到明确提醒并人工完成验证，以便知道哪一步需要我。
6. 作为运营者，我想配置门店与巨量引擎广告账户的多对多映射，以便线索成本按门店正确归因。
7. 作为运营者，我想通过 OAuth 授权巨量引擎广告账户，以便经官方 API 拉取报表。
8. 作为运营者，我想看到所有门店的汇总看板（各店线索量、消耗、线索成本），以便快速掌握整体经营状况。
9. 作为运营者，我想在看板切换时间范围（今日/近7天/近30天/自定义），以便看不同周期趋势。
10. 作为运营者，我想按门店筛选看板与明细，以便关注特定门店表现。
11. 作为运营者，我想看板支持下钻到广告计划层级（各计划消耗/线索量），以便判断哪个计划效果好。
12. 作为运营者，我想查询线索明细（时间、门店、意向车型、手机号、状态），以便下钻到具体线索。
13. 作为运营者，我想按线索状态筛选明细，以便看未跟进/已跟进等状态分布。
14. 作为运营者，我想导出看板数据或线索明细为 Excel，以便进一步分析或汇报。
15. 作为运营者，我想让客户端每小时自动拉取新数据，以便看板当天足够新鲜。
16. 作为运营者，我想让客户端每小时重拉最近 7 天线索窗口，以便线索状态变更及时反映。
17. 作为运营者，我想让客户端每日做一次导出对账，以便增量遗漏的变更被快照纠正。
18. 作为运营者，首次使用时我想回填 90 天历史数据，以便看板一开始就有趋势。
19. 作为运营者，我想手动触发「立即拉取」，以便刚配置完不用等整点。
20. 作为运营者，我想看到各门店采集任务的运行状态与最近成功时间，以便及时发现数据停更。
21. 作为运营者，当某店会话失效且无法自动恢复时，我想在看板看到明确标记，以便知道哪店数据是旧的。
22. 作为运营者，我想让敏感凭证（巨懂车密码、会话 cookie、巨量 token）存系统凭证库而非业务数据库，以便缩小泄露面（库里全是客户手机号）。
23. 作为运营者，我想多门店账号并行采集，以便所有店同时保持最新。
24. 作为运营者，我想在 Windows 和 macOS 上安装使用，以便我和助理各自的电脑都能跑。
25. 作为运营者，我想界面为简体中文，以便助理上手无门槛。
26. 作为运营者，我想把安装包直接发给助理安装（无应用商店、无自动更新），以便分发尽量简单。
27. 作为运营者，数据为空/加载中/出错时我想看到明确的界面状态，以便区分「没数据」和「坏了」。

## Implementation Decisions（实现决策）

- **技术栈**：Tauri 2 + Rust 后端 + Vue 3 + TypeScript（ADR-0002）。
- **集成策略**：巨量引擎走官方 Marketing API（OAuth 授权，账户+计划层级报表）；巨懂车经营后台爬取（ADR-0001、ADR-0003）。
- **巨懂车取数**：内嵌 WebView 完成登录并捕获会话；主路径为复用会话直调「线索管理」列表页 JSON 接口，按时间窗口增量拉取，每小时顺带重拉最近 7 天窗口覆盖状态变更；每日一次「导出表格」对账快照；全部按线索 ID upsert 合并。
- **会话失效重登顺序**：WebView 内自动回填账号密码（滑块人工完成）→ 真人短信验证码兜底。
- **存储**：业务数据本地 SQLite；凭证（密码、cookie、token）存系统凭证库（Windows Credential Manager / macOS Keyring）。
- **账号模型**：门店是管理单位，每店一个巨懂车账号；门店↔广告账户多对多，使用者配置。
- **调度**：每小时拉取；首次使用回填 90 天。
- **部署形态**：纯单机，每台机器独立安装、独立采集；巨懂车会话互踢实测后再评估采集端分离。
- **分发**：手动安装包（Windows .msi/.exe、macOS .dmg），无自动更新。
- **模块划分**：Rust 侧为巨懂车采集器、巨量采集器、存储仓库、查询服务（Tauri command 边界）、调度器、凭证管理；前端为看板页、明细页、门店/账户设置页。

## Testing Decisions（测试决策）

- 好测试只断言外部可观察行为（SQLite 内状态、command 返回值、生成的导出文件），不测内部函数与实现细节。
- **入库接缝**：录制的真实响应（巨懂车列表 JSON、导出 xlsx、巨量 API 响应）作为夹具，回放驱动「拉取→解析→按线索 ID 去重合并」，断言库内结果；关键断言是幂等——同一夹具跑两遍库不变。
- **出库接缝**：seed SQLite 后直接调用 Rust command 函数（不启动 UI 与 WebView），断言看板聚合、筛选、导出内容。
- 夹具来源：spike 与日常运行录制的真实响应，脱敏后入库。
- 先例：空仓库，本 spec 即测试先例。
- 不做自动化：Vue 组件（人工验收）、WebView 登录流程（人工）、真实平台联调（手动冒烟）。

## Out of Scope（不做）

- 线索跟进/分配管理（DMS 职能）
- 异常预警（第二版）
- 自动更新、多租户、对外分发
- 巨量千川、本地推等其他巨量系平台
- Linux 支持
- 服务端与多人数据同步（除非实测互踢后重启讨论）

## Further Notes（附注）

- **立即启动**：巨量引擎开发者申请（企业主体、代理商型、报表权限），周期以周计，卡住巨量侧一切后续。
- **首个 spike**：巨懂车列表接口带会话 cookie 直调是否被签名拦截——决定主路径成立与否；spike 时同步录制测试夹具。
- 待验证：导出频率限制、「导出记录」保留条数、导出文件有效期。
- 词汇与决策记录见 GLOSSARY.md 与 docs/adr/0001–0003。
